# Result: 0.6.0 loopback cache-hit baseline

This page records the numbers behind the README performance table. It is a host-
specific measurement, not a promise about other hardware. Methodology and
switches are in [Benchmarking](../benchmarking.md).

## Build and environment

| Field | Value |
|---|---|
| Version | dns-rs 0.6.0 |
| Commit | `3d58c19c393af7f2e59522342223547c1820f70a` (`v0.6.0`; worktree clean) |
| Date | 2026-11-20 |
| Rust | `rustc 1.100.0 (0ef1bc386 2026-11-09)`, `cargo 1.100.0` |
| OS/kernel | Linux 7.3.4-3-t2-resolute, x86_64 |
| CPU | Intel Core i7-9750H @ 2.60 GHz, 6 cores / 12 threads |
| Memory | 15 GiB total; host shared with desktop workloads |
| Build | `make bench` default release profile; no `RUSTFLAGS`, no `target-cpu=native` |
| Resolver | host binary `target/release/dns-rs`, CPUs 0-3 |
| Load generator | `scripts/dns-bench.rs`, CPUs 4-11 |
| Scenario | `hit`: 4,000 distinct names, 8 queries in flight, 5 s warm-up, 10 s measured |

The resolver used a stub zone backed by `scripts/dns-bench.rs serve` with a
3,600-second TTL. All measured answers were message-cache hits. Four thousand
names fit below the 8,192-entry message cache, so there was no eviction during
the measured window.

## Reproduce

```bash
git checkout v0.6.0
make bench
```

Two consecutive invocations were recorded; the resolver binary was already
built for the second run.

## Summary

| Workers | QPS, two runs | p50, two runs | p99, two runs |
|---:|---|---|---|
| 1 | 75,359 - 85,209 | 54.1 - 54.6 us | 107 - 282 us |
| 2 | 101,158 - 120,200 | 33.0 - 35.8 us | 76 - 217 us |
| 4 | 114,615 - 120,785 | 26.4 - 33.8 us | 173 - 184 us |

Both runs reported `errors=0` and `rcode=0`. The spread between runs is larger
than the difference between two and four workers in one run, which is why the
README treats throughput differences at that scale as indicative only. Tail
latency is especially sensitive to the shared host: the maximum single-sample
RTT exceeded 5 ms in every run.

RSS is `VmRSS` at idle and `VmHWM` after the cache was filled, read from the
resolver process. mimalloc commits memory in steps, so small RSS differences
between runs are not meaningful.

## What this does not measure

This is a warm cache-hit workload only. It does not cover cold iteration, cache
misses with a real upstream, DNSSEC validation, TCP framing, DoT, mixed
workloads, or connection churn. See
[Limitations](../limitations.md#benchmark-coverage) for the full list.
